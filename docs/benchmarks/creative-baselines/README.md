# 创作验收基线脚手架

这里固定三份可在本机重建的输入：双人对白、动作衔接、强风格。它们尚未执行真人创作测试或真实平台生成，所有测量值都保留 `null`，质量均为 `pending-manual`。单元测试中的合成事件仅检查计数逻辑。

复现时新建独立项目，将 `brief` 写进梗概，将 `shots` 写入分镜表，按 `characters` 准备角色设定与音色，并选定 `trialShotId`。先只运行该镜头，完成后人工检查 `manualChecks`；明确确认前不批量运行后续镜头。固定输入不意味着输出质量已通过。

每次运行保留独立 `runId`、应用版本、平台与模型版本、开始/截止时间和证据文件路径。可以使用本机 mock 验证流程；mock 与真实平台测量必须分开，不混入同一组质量结论。调用真实平台仍需要单独的明确执行授权。

计数方法：

- 首镜完成：在本次预先记录的截止时刻，选定镜头的图像、视频及所有计划对白/音效都有可读取的当前采用结果。失败记为 `false`，未测量为 `null`。完成不代表人工质量通过。
- 首镜完成率：同一条件下，首镜完成的运行数 / 已观测运行数，同时列出未测量运行数；不得把待测运行补成成功。
- 人工操作数：记录完整任务范围内每个真实用户动作的唯一事件 ID；一次点击、一次字段提交、一次选项改变或一次人工审片确认各计一次，不按底层键盘字符数累加。没有完整动作记录时保留 `null`。
- 视频 submit 数：只计实际 `video.generate` 提交入口的调用次数，包括失败、结果未知和重提；poll、下载、恢复查询与候选数量都不能代替 submit。每次真实提交使用独立事件 ID，并保留日志或 trace 证据；缺少完整记录时保留 `null`。

`schema.json` 约束输入和待测字段；镜头结构同时按 `@plein/nodes` 的 `Shot` 校验。`baselineMetrics.ts` 只汇总带证据的观测，并拒绝重复运行或重复事件。人工风格、声音和动作质量仍由审片意见记录，不能从生成成功率推导。

## 本轮机器流程测量

独立运行器会启动临时本机 HTTP 服务，仅启用 mock 平台，实际调用节点执行器和 FFmpeg。它不需要前端构建：

```sh
pnpm --filter @plein/server exec tsx bench/workflow-baselines.ts --output ../../test-results/workflow-baselines.json
```

每类只展开 `trialShotId` 指定的一镜，执行图像和计划对白、脚本审片标记、两次本地样片导出、一次视频生成、首镜成片交付、一次仅视频的局部返工和新版本导出。它会检查样片重复导出没有额外模型提交、未返工节点候选未变、旧候选保留、未解决交付意见阻止确认、新导出不继承旧确认。其余镜头没有生成，不能由此宣称双人质量、跨镜连续性或整片创作已验收。

提交次数由本次服务的 `mockProvider.submit` 调用入口直接记录，不用 HTTP 运行请求数、poll 或候选数量估算。报告分别列出每阶段提交事件、候选 ID 和脚本命令次数；脚本命令不是人工操作次数。视频 mock 内容固定，素材去重与候选身份分别检查，不能把新候选解释为画面质量发生变化。

报告含 Git 基点、工作区是否有改动、tracked diff 摘要、fixture SHA-256 和计数口径。生成素材经真实 HTTP 读取并验证哈希，导出视频经本机 ffprobe 检查，证据文件保存在 `test-results/workflow-baseline-artifacts/`。临时服务数据在结束后删除；加 `--keep-data` 可留作排查。

即使机器流程全部通过，人工首镜成功率、人工操作数、真实费用仍保持 `null`，创作质量保持 `pending-manual`。运行器里的“可用”和交付确认是带明确注释的脚本测试动作，不是用户或人工审片记录。首次运行后才能引用生成的测量报告；脚本和单元测试通过本身不等于这些场景已经实测。
