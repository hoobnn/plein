# 0.1.0 验收流程

2026-10-12 起，roadmap 的每个实现都按本文件的四层流程验收。目的是让「源码存在」和「真的能用」分开：代码合并不等于能力交付，每一层都要留下证据。

## 为什么分四层

roadmap 第三节已经写明，流程验收与成片质量验收要分开记录。这里再具体化：

- 单测能证明数据关系和分支逻辑，证明不了 ffmpeg / 平台接口 / 界面点击。
- mock 平台能证明画布编排与任务调度，证明不了真实模型的输入是否生效。
- 真实样例会产生调用费用，并需要人工审看回放，不能作为每次改动的门禁。

所以每层有明确的准入和结论写法，缺哪层就写「未验收」，不许含糊过去。

## 四层流程

| 层          | 做什么                                                                                          | 门槛                                                           |
| ----------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| L1 单元     | 纯函数：差异计算、参数校验、ffmpeg 参数拼装、缓存键                                             | 新增逻辑有对应用例；边界与错误分支有用例                       |
| L2 集成     | mock Provider（`PLEIN_MOCK_PROVIDER=1`）完整验证节点运行、缓存、导出；媒体加工用本机真实 ffmpeg | 端到端状态与产物断言通过，不靠日志人工判断                     |
| L3 运行冒烟 | 真实起服务，按用户路径点一遍（见下）                                                            | 关键路径可用；失败有可执行提示，不是 cryptic 报错              |
| L4 真实样例 | 真实平台调用与人工回放                                                                          | **需要用户授权与密钥**，默认不做；未做就写「未验收（待授权）」 |

L1–L3 是合并门禁，L4 是发布门禁。mock 通过不能替代 L4，这一点 roadmap 第二节已经写明，不再重复。

### L3 运行冒烟的固定路径

```bash
pnpm e2e            # 自动化部分：构建 e2e 前端，基于 mock 平台启动真实服务，由 Playwright 自动完成下面 1–5 步
pnpm dev            # 手工走查时用：服务端 + 前端
```

`pnpm e2e` 首次运行前要装一次浏览器：`pnpm exec playwright install chromium`。

1. 首页新建画布，导入一张图片、一个视频、一个音频、一段 Markdown；
2. 设置页启用 mock 平台（开发时用 `PLEIN_MOCK_PROVIDER=1`），完整运行文本 → 图片 → 视频 → 配音 → 配乐；
3. 完整执行一遍本次交付的用户路径（例如「展开分镜 → 批量出图 → 导出 MP4」）；
4. 刷新页面、停掉服务重启，确认元素、资产、引用、任务记录都还在；
5. 制造一次失败（例如选一个没配密钥的平台），确认节点上给出可读的失败原因。

第 4、5 步是 roadmap 对 0.1.0 的硬要求（「刷新 / 重启后不丢」「失败任务能明确恢复或核查」），每次验收都要真的做，不能只运行单元测试。

## 环境差异必须如实记录

本机 ffmpeg 是 Homebrew 构建，**不含 libass**，`ass` 滤镜不可用；Docker 镜像里有。涉及字幕烧录的验收：

- 有 libass 的机器：运行完整的导出断言；
- 没有 libass 的机器：运行「关闭字幕也能导出」的结构用例，并验证「要字幕时提前报可执行错误」。

不允许把跳过（skip）写成通过。`apps/server/src/assets/media.ts` 的 `mediaCaps()` 就是为此存在的：缺能力要在合成前说清，而不是让 ffmpeg 抛一句 `Error parsing a filter description`。

### E1-4 基础媒体加工

源码已实现，L1–L3 通过（含真实 ffmpeg）；**界面点击未验收**。

- 加工能力集中在服务端 `deriveAsset()`，前端工具条与 Agent 共用：`POST /api/media/derive`，产物永远是新资产 + 旁挂来源记录，源资产字节不变（「源视频一个字节都没动」用 sha256 比对）。
- 图像坐标按显示像素（含 EXIF 方向）：「裁剪：矩形坐标对应实际像素」「orientation 6 的图显示为 20×40」。
- 变速音画同步：`setpts` + `atempo` 串联；并修掉一个真实缺陷——`setpts` 不改最后一帧时长，变速后会多出约两帧导致音画错位，已按 `probe.duration / speed` 加 `-t` 兜底，并有回归测试（去掉修复即失败）。
- 音视频分离、任意时刻抽帧资产化、音频截取 / 切分 / 变速都有对应测试。

- L3：`pnpm smoke` 里加了裁剪加工 → 新资产 16×8、源资产仍是 32×24 的断言。

### 0.1.3 缓存与断线重连（2026-10-15）

`e2e/offline.spec.ts`，进 `pnpm e2e`。断线有两种做法：拦截同步 WebSocket（页面和素材照常从服务端取，只断文档同步），以及真的杀掉服务进程再起来（用例自己在另一个端口起一个服务）。

| 场景                     | 结果                                                                                                                    |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| 已打开画布断线编辑       | 断线后状态显示「离线 · 改动先存在本机」，照常加节点                                                                     |
| 断线时刷新               | 从 IndexedDB 缓存打开，断线前后的改动都在；服务端此时只有断线前的内容；恢复连接后合并上去，无缓存的新页面能看到全部改动 |
| 服务崩溃后重启           | 服务被强杀期间继续编辑，重启后自动重连，改动合并到服务端                                                                |
| 旧 schema 的缓存         | 不先显示，等服务端同步后再迁移                                                                                          |
| 打开已在别处删除的画布   | 回首页并提示「画布不存在或已被删除」，本机缓存清掉                                                                      |
| 断线期间加载失败的预览图 | 重连后自动重新加载                                                                                                      |
| IndexedDB 不可用         | 照常从服务端打开、没有页面错误；断线时提示「离线 · 改动未保存」（只在这个页面里，刷新会丢）                             |

状态点区分：连接中、本机缓存（先显示缓存，还没和服务端对上）、同步中、已同步、离线；悬停有完整说明。离线说明里写明没加载过的素材暂时显示不了：素材只从服务端读取。

**入口不能离线打开**：前端由同一个服务托管，没有 Service Worker。服务停着时新开页面打不开（用例断言了这一点），所以「首次离线启动」不在支持范围；缓存只帮已经能打开页面的情况（服务重启、网络抖动、刷新时同步还没连上）。OPFS 全素材离线另行设计。

验收中发现并修复：

| 问题                                                                           | 根因                                                                                                  | 处理                                                                            |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 打开已在别处删除的画布，一直停在缓存里的旧画布上、显示「连接中」，改动无处可去 | 服务端对不存在的画布在握手时回 HTTP 404，浏览器拿不到握手失败的状态码，y-websocket 只会无限重连       | 先完成握手再以 4404 关闭，前端照已有逻辑清缓存回首页                            |
| 删除画布的提示一闪就没                                                         | 提示显示在画布页，跳回首页时画布页已卸载                                                              | 首页也显示画布留下的提示                                                        |
| 断线期间没加载出来的预览图，重连后一直是占位卡片                               | 渲染器记住了失败的地址，同一地址不再加载                                                              | 失败时忘掉地址；同步对齐后（从缓存打开、断线重连）重画全部元素，失败的重新加载  |
| 服务没起来时从缓存打开的画布显示「连接中」而不是离线                           | 一次都没连上时 y-websocket 不发「断开」状态                                                           | 连接关闭就记为离线                                                              |
| 服务停着时新开页面还能拿到旧的 `index.html`                                    | 前端页面没有 `Cache-Control`，浏览器按 `Last-Modified` 启发式缓存；升级后也可能拿旧页面找不存在的脚本 | `index.html` 等每次回服务端确认（`no-cache`），`assets/` 下带哈希的产物长期缓存 |
| IndexedDB 被禁用时页面报未处理的 Promise 错误                                  | y-indexeddb 内部的 Promise 没接 catch                                                                 | 先同步探一下 `indexedDB`，不可用就不建缓存                                      |
| 删除项目后它的画布缓存留在浏览器里                                             | 只有删画布时清缓存                                                                                    | 删项目时一并清掉其画布的缓存                                                    |

| 完成可用镜头的生成次数  | 要按镜头人工判定可用                                    | 用上次 L4 的数据目录统计，零调用                                                                                          |

L4 用例在 `e2e/real/drama.l4.ts`，单独的配置 `e2e/playwright.l4.config.ts`，不进 `pnpm e2e` 和 CI。它自己起停服务端，分两个用例：

- 出片：模板改成 6 镜头 → 剧本、抽取、设定卡（核对参考图节点、音色）→ 展开（核对镜头 @ 到角色、场景、道具）→ 批量分镜图 → 批量视频，等至少一个视频已提交到平台后强杀服务端再起来，核对重启前后任务记下的远端调用一致（续查原任务、没有重复提交）→ 批量配音 → 配乐 → 导出。
- 资产库：出片画布上的卡片存入资产库，在新项目按类别取用。该用例不产生调用费用，可以用 `PLEIN_L4_CANVAS=<画布 id> pnpm e2e:real --grep 资产库` 单独运行。
- 0.2：在出片画布上核对实际输入与上次提交一致；改第三镜头后从「查看影响」按推荐默认重做（分镜图、配音各一次，视频保留）；导出项目包、在全新数据目录导入并重新合成；外部应用经 MCP 提修改方案，只改文字（零调用）、只给第四镜头出候选图（一次）。可以用 `PLEIN_L4_CANVAS=<画布 id> pnpm e2e:real --grep 0.2` 单独运行。

前一次在出图之后断了，可以用 `PLEIN_L4_RESUME=<画布 id>` 接着跑出片用例（跳过剧本、设定卡和展开）。

镜头视频默认用 MiniMax H3、768P（`PLEIN_L4_VIDEO_MODEL` / `PLEIN_L4_VIDEO_RESOLUTION` 可改，模型给空串按模板默认）。数据目录里先不启用视频平台：用例在批量生成视频前才在设置里启用它，视频全部完成后停用。这是为了绕开当时的自动选模型（会把其余环节和设定卡音色换到视频平台上）；改成默认模型后已不必要，用例暂时保留这一步。

```bash
PLEIN_L4_DATA=<配好平台的数据目录> PLEIN_FFMPEG_PATH=<带 libass 的 ffmpeg> PLEIN_FFPROBE_PATH=<ffprobe> pnpm e2e:real
```
