## 局部返工操作数

固定六镜头案例（短剧模板，六个镜头已出分镜图、视频、配音），在分镜表里改第三镜头的台词和分镜图提示词，到第三镜头换上新结果为止。操作只计用户意图上的一步：点按钮或菜单项、填一个输入框、按一次 Esc；镜头移动和等待不计。付费提交按新建的分镜图、视频、配音任务计。

| 路径                                     | 版本        | 操作 | 付费提交 | 其余五个镜头被改 | 第三镜头换掉       |
| ---------------------------------------- | ----------- | ---- | -------- | ---------------- | ------------------ |
| 分镜表三个批量按钮                       | 基线 / 当前 | 9    | 14       | 5                | 分镜图、配音、视频 |
| 右键分镜图「运行下游」+ 右键配音「生成」 | 基线 / 当前 | 11   | 3        | 0                | 分镜图、配音、视频 |
| 查看影响，三项都勾上重做                 | 当前        | 9    | 3        | 0                | 分镜图、配音、视频 |
| 查看影响，按推荐默认（视频建议保留）     | 当前        | 8    | 2        | 0                | 分镜图、配音       |

- 基线和当前在共有的两条路径上结果相同：W2 没有改变原有路径。
- 基线里模板引导的批量按钮会把六个镜头全部重跑（14 次付费提交），其余五个镜头的结果也被换掉；只动第三镜头要知道右键「运行下游」再单独生成配音。当前从分镜表点「查看影响」就能只重做第三镜头，步数比右键路径少 2 步，并且能按建议保留视频，少一次视频提交。
- 本次测量等待「查看影响」面板在文档变化后停 0.8 秒重新分析，再进行勾选。2026-10-16 补正：重新分析期间暂停选择与执行，只接受最新响应，建议未变时保留用户勾选；旧测量值未因本次修复重新测量。

## 失败恢复时间

单个 `plein/image` 节点，mock 生成耗时 600 ms；自动重试退避用默认的 2 s、8 s。耗时从注入故障到结果入库，不含人的反应时间（任务一变成失败脚本就立刻操作）。submit 次数即付费提交次数。所有场景最后都只入库一份结果。

| 故障                          | 版本        | 用户操作                 | submit | 恢复耗时    |
| ----------------------------- | ----------- | ------------------------ | ------ | ----------- |
| 提交未知（回应丢失）          | 基线        | 重新运行                 | 2      | 0.63–0.68 s |
| 提交未知，平台有 `lookup`     | 当前        | 无                       | 1      | 0.65 s      |
| 提交未知，填平台任务 ID       | 当前        | 「填写平台任务 ID」      | 1      | 0.64 s      |
| 提交未知，确认未受理后重提    | 当前        | 「确认未受理，重新提交」 | 2      | 0.62 s      |
| 轮询连续 2 次失败             | 基线 / 当前 | 无                       | 1      | 10.05 s     |
| 轮询连续 3 次失败（重试用完） | 基线        | 重新运行                 | 2      | 10.63 s     |
| 轮询连续 3 次失败（重试用完） | 当前        | 「重新获取」             | 1      | 10.05 s     |
| 轮询期间服务重启              | 基线 / 当前 | 无                       | 1      | 0.62 s      |
| 下载 503 一次                 | 基线 / 当前 | 无                       | 1      | 2.02 s      |
| 结果地址过期（403）           | 基线        | 无                       | 1      | 2.02 s      |
| 结果地址过期（403）           | 当前        | 无                       | 1      | 0.02 s      |
| 写入资产库失败一次            | 基线        | 重新运行                 | 2      | 0.63 s      |
| 写入资产库失败一次            | 当前        | 「重新获取」             | 1      | 0.03 s      |

- 提交未知的耗时差别在 mock 下看不出来（故障紧跟提交，接着查原任务和重新提交都要等生成）；真实平台上接着查原任务省掉的是整段生成时间和一次费用。内置真实平台都没有 `lookup`，实际走「填平台任务 ID」或「确认未受理后重提」，后者在平台其实已受理时会重复计费。
- 测量时发现：轮询一直失败、自动重试用完后，当前版本原先也只能重新运行（多一次提交）；已修复，失败时记为平台已受理（`remote_pending`），可以重新获取。

## 迁移成功率

基线没有项目包，只能整目录复制数据目录，没有可比的测量。当前：正常包 10/10 导入成功，损坏包 30/30 被拒绝且目标目录无残留，错误码与提示 30/30 说清原因（测量中修了两处：截断的包原先被说成「不是项目包」，清单超过 64 MB 原先报哈希不符）。

- 正常包：六镜头短剧（当前结果 / 含历史候选 / 同目录再导入为副本）、引用全局资产库条目（目标目录有 / 没有同 id 条目）、空项目（一张空画布 / 没有画布）、三张画布共用素材且导出时有运行中的任务、带智能体会话和保留决定（按设计不迁移）、导出时就缺素材。判定：导入成功、暂存目录清理、画布能打开、所有素材可读且哈希等于 id、各类数量与包一致、有序列的能用本机 ffmpeg 合成、再导出与第一次导出在 id 映射后一致。
- 损坏包：不是 zip、三种截断、缺清单、素材 / 画布哈希不符、素材 / 运行记录缺失、清单版本过高 / 为 0 / 为字符串、格式名不对、尺寸为负、缺字段、清单不是 JSON、素材 id 与内容不符、五种路径穿越、两种重复条目、声明 5 GB、压缩炸弹、清单超过 64 MB、画布文档 / 运行记录内容损坏、不支持的压缩方式。判定：返回 422，项目 / 画布 / 条目 / 任务 / 素材行数和素材文件数不变，暂存目录为空。
- 未覆盖：4 GB 上限（要真写 4 GB）；本机 ffmpeg 没有 libass，字幕烧录没验证（字幕设置随包保留）。
