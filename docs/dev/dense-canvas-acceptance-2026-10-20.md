# 密集媒体画布与大范围适配验收

本轮关闭固定规模下的交互缺口，并修复一个实际截图暴露的问题。性能结果存在跨批次波动，单独保留待查，不把交互通过写成性能整体通过。

## 实际问题与修复

千媒体加六十节点、五十九条连线的画布整理后，适配比例被相机的 5% 下限卡住，导致两侧元素落在侧栏后方或窗口之外。原生产构建的范围断言失败：元素左边界为 261.2，相机可见区域左边界为 284。截图也显示左右裁切。

相机现在根据目标计算完整适配比例；程序定位可以扩展最小比例，后续滚轮与定位动画沿用这个下限，避免跳回 5%。没有经历大目标适配时，普通滚轮仍保持原来的 5% 下限，最大比例仍为 800%。适配目标的计算保持无副作用。极窄视口计算可用宽高时至少保留一个像素，避免负比例。

缩放菜单在低于 1% 时显示两位有效数字，并允许小数输入，避免大范围全景显示为 0% 或输入时丢失小数点。普通比例沿用整数显示。

## 交互与资源范围

新增 `e2e/canvas-dense.spec.ts`，使用真实上传的固定媒体夹具，不调用计费模型。夹具构建使用测试入口，以下交互使用实际鼠标、键盘和界面按钮：

- 一千个媒体元素、三十二张不同图片、一段视频与一段音频；框选十二个媒体元素，两次快捷键分组，拖动外层组。核对十二个元素同向等距移动、尺寸和素材不变，其余元素完全不变；撤销重做核对完整元素及连线快照。
- 实际滚轮平移、Ctrl 加滚轮缩放不改写文档；连续五次退出和重新进入，核对文档保留、预览恢复。每次退出后所有受管理纹理 owner、租约、排队／进行中的加载及已加载／卸载纹理归零。此检查不是浏览器总内存或硬件显存测量。
- 一千个媒体加六十个局部重绘节点，先建立五十八条边，再实际拖动端口新增一条指定连接；撤销重做恢复完整快照。整图整理、还原和重做保留素材、参数及连线，只改变位置。
- 整理后检查全部一千零六十个元素的世界矩形都投影在相机避开面板后的可见区域。再将一个节点放到五百万世界单位处，核对低于 1% 的显示、小数输入和整图定位动画实际到达目标比例。
- 同批补验既有低缩放小图、离屏回收、预览 HTTP 失败门禁、相机导航接管、窄屏底栏和常用 UI 操作。

相机定向单测 17 项通过，覆盖巨大横向／纵向目标、面板避让、滚轮连续性与程序定位。最终画布核心及性能比较器 11 文件、84 项通过；测试、画布核心与 Web 三处 TypeScript 检查通过。生产构建与开发 StrictMode 各 22 项组合全部通过，均包含新增两项密集画布回归。定向源码格式／lint、文档 Markdown 检查通过。

本轮以 8893／8894 独立端口、临时数据和独立构建执行。复跑入口为普通 `e2e/playwright.config.ts` 与开发 `e2e/playwright.dev.config.ts`，选择 `canvas-dense.spec.ts`、`canvas-media.spec.ts`、`camera-navigation.spec.ts`、`canvas-footer-fit.spec.ts` 和 `ui.spec.ts`；开发配置已补入密集画布及媒体回收两份测试。

[整理后完整适配截图](../benchmarks/2026-10-20-dense-arranged.png)已人工复查：全图保留在侧栏右侧与窗口以内，底栏和整理确认按钮可见。独立测试服务、临时夹具、构建与跟踪文件收尾清理。

## 性能证据与未关闭项

产品基点为 `71e0127`，测量时仅测试工具及夹具有未提交改动；两批使用同一个生产构建，均在本次适配修复之前。旧基线自身也标记 `sourceDirty=true`，不能仅通过它记录的 commit 精确复建当时源码。没有覆盖或替换旧基线。

测量环境：macOS arm64、Node 26.12.0、Chromium 156.0.8078.4，1440×900，ANGLE Vulkan SwiftShader 软件光栅；每批三轮。环境、夹具及指标集合通过现有比较器核对。真实媒体用于冷／热打开；五个交互性能场景使用原有演示画布，不能当作真实媒体交互耗时。软件光栅数据也不能宣称触控板或硬件 GPU 帧率。

| 媒体就绪中位数 | 10 月 17 日基线 | 本轮初测 | 相同构建复核 |
| -------------- | --------------- | -------- | ------------ |
| 冷开首预览     | 748.6ms         | 1096.4ms | 969.4ms      |
| 热开首预览     | 595.8ms         | 958.0ms  | 791.5ms      |

初测的热开首预览和媒体就绪触发既定回归门槛；复核未触发门槛。初测三次热开分别为 958、563.1、1108.2ms，复核分别为 791.5、801.5、786.2ms。保留两批，不能选择较快一批宣称修复。两批各五个交互场景未触发回归门槛，未记录到交互长任务或预览加载失败。

额外热开 CPU 采样中 `getProgramParameter` 自耗时约 408ms、`bufferSubData` 约 259ms；采样本身会扰动耗时，只用于定位方向，尚不足以认定某处产品代码为根因。因此本轮没有宣称修复性能回归，也没有改变门槛或降低夹具规模。

## 10 月 21 日：预览程序精简与交替复测

在同机、相同 1000 元素／32 张图片／视频／音频夹具、三轮采样下，依次测试原构建、候选、原构建复核、候选复核。两批完整交互和后续仅打开复核分别配对，未改变已有比较门槛。原构建为 `be4da90` 对应的 `dist-schema-live`；候选以相同产品代码加入本次预览程序精简。报告中的 sourceCommit 是执行时仓库 HEAD，构建来源由本段及结构化验收记录明确，不能把它当作两个构建相同的证明。

| 首个可见预览中位数 | 原构建  | 候选    | 原构建复核 | 候选复核 |
| ------------------ | ------- | ------- | ---------- | -------- |
| 冷开               | 921.5ms | 963.6ms | 1105.5ms   | 934.1ms  |
| 热开               | 884.3ms | 659.6ms | 759.9ms    | 662.2ms  |

候选两批热开中位数分别改善约 25.4% 和 12.9%。原构建和候选的样本仍有重叠，冷开也不呈单向改善；因此本轮只确认当前软件光栅环境下的热开改善，不宣称消除全部启动波动。完整对照的缩放 JS 中位数为 4.604 → 4.549ms／帧；其余四个交互场景亦未触发既定门槛，长任务为零，六次打开各有 1000／1000 预览成功。复核只重测打开，不冒充第二批完整交互。

实现保留 Pixi 的图形、颜色、变换和像素取整程序片段，将已加载预览使用的纹理采样器从通用配置缩减为两张。普通大小的预览原本已经不合批，不将其强制改成动态批处理；小卡片与极端长宽比的内嵌预览沿用默认策略。WebGPU 沿用默认程序。每个引擎拥有独立 Shader，销毁时释放自身绑定，保留可能被其他引擎使用的缓存 Program。

此前两个强制批处理候选虽缩短打开时间，却将缩放 JS 推高到约 38.3 和 31.5ms／帧，均已放弃；这些负面结果未用于替换本次原构建，也没有进入最终源码。

新增实际像素回归使用上传的 RGB 和半透明 PNG，同时检查普通媒体和图像节点。基线及候选均验证缩放、检查点预览、关闭预览以及恢复为新画布后颜色正确、原文档不变、纹理 owner 回到一个；检查点预览还逐像素确认四种颜色，而不只依赖资源 ready 统计。恢复截图已人工检查。
