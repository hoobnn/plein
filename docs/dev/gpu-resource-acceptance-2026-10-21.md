# 卡片图形所有权与静止 GPU 回收验收

## 已复现的问题

十分钟会话后 GC 堆增长约 16.3MB，原记录保留。本轮在相同千媒体／六十节点／五十九连线场景中进一步预热并快速操作，采集堆快照和无快照对照；不把原增长全部归给单一原因。

堆快照中主引擎、场景、视图集合、文档和 renderer 实例数保持一个，增长集中在图形数组和 GL 缓冲。构造函数经构建压缩，多个类型都名为 `e`，这类名称不能用作独立 App／Y.Doc 实例计数。无快照对照也出现相似增长，排除了快照是唯一原因的假设。

无快照对照的快速操作后 JS 堆约 258.2MB；静止 95 秒后约 256.5MB，GPU 回收标记已就绪，但仍有 22214 个 GL 缓冲。一次实际平移后，渲染后的回收立即执行，缓冲降到 2124，堆降至约 85.4MB。这证明静止按需画布未执行应有的回收，而不是仅根据堆峰值猜测泄漏。

## 原因与修复

内置卡片以 `display.destroy({ children: true })` 销毁容器。Pixi 8.22 的 Graphics 在收到该对象参数时，只有显式 `context: true` 才销毁自有 GraphicsContext；原写法让旧 context 及绘制数据留给延迟回收。七类内置卡片的真实 context 生命周期单测在原实现全部失败。

内置 renderer 现在显式销毁自身创建的 context。参数只包含 children 与 context，素材纹理继续由纹理池共享和释放，Shader 继续由引擎拥有。自定义 renderer 的销毁实现不受该内部辅助函数影响。

Pixi 默认闲置期限为 60 秒、检查周期为 30 秒，实际回收位于 postrender。按需画布静止后没有渲染，导致已经到期的任务一直等待。引擎现在通过 Pixi scheduler 每 30 秒请求一帧，按原期限执行 GPU 回收；引擎销毁时取消调度。持续交互中该请求与原有脏帧合并，静止时仅低频提交一帧。

新增浏览器回归仅观测原生 createBuffer／deleteBuffer，使用 WeakSet，不保留缓冲强引用，不主动调用渲染或 GPU GC，也不改变默认期限。原构建在真实 95 秒闲置后仍保留 242 个缓冲，空画布基线为 2，未通过最多额外 8 个的约束。

## 最终验收

修复提交 `14d070d`。核心 11 文件／88 项通过，canvas-core／Web／root 三处类型和改动文件格式／lint 通过。真实 Metal 四项、软件生产两项、开发 StrictMode 十五项通过，覆盖真实 GPU 闲置回收、RGB 和半透明像素、context 恢复、千媒体操作及检查点生命周期。新闲置用例在候选 Metal 上实际等待 95.013 秒，242 个缓冲中显式删除 240 个，剩余 2 个与空画布一致；返回后像素和完整文档正确。

同一千媒体对照在候选上快速操作后堆约 58.7MB，静止 95 秒后约 58.6MB，GL 缓冲为当前可见内容所需的 2124 个；后续一次平移后约 57.8MB，不再需要该操作才大幅回收。原构建对应阶段为 258.2／256.5／85.4MB、22214／22214／2124 缓冲。两套均无堆快照，均保持原 GPU GC 配置和真实时间；候选重载后文档与千媒体预览保持。

此处统计原生 API 缓冲和受管理资源，不直接测量驱动显存。快速操作对照不是第二次十分钟持续会话，原十分钟 16.3MB 增长记录保留；本轮证实并修复其中一项资源管理原因，没有断言全部增长均已归因或完全无泄漏。
